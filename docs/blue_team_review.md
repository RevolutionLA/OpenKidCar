# 干杯一号（OpenKidCar）蓝军评审报告

- **评审日期**：2026-08-10
- **评审视角**：蓝军（对抗性 / 找茬），聚焦**真实硬件落地前的隐患**
- **评审范围**：固件 `firmware/arduino`、大脑 `software/raspberry_pi/car_brain`、数字孪生后端 `digital_twin/backend`、协议文档 `docs/communication_protocol.md`
- **评审方式**：代码 + 协议文档 + 硬件部署指导书 三方对照，验证"文档宣称的能力"是否在代码里真实存在
- **评审结论**：**仿真层完成度高、真实层几乎未验证。** 最大的风险不是代码写错，而是"文档 + 演示看起来就绪，导致带着没上过真车的代码直接上真车"。

> 给开发的话：本报告每条问题都带【证据】【影响】【修复建议】【验收标准】，按编号逐个修，改完一项勾一项。**上真车联调之前，请至少把 P0 三项清零。**

## 一、硬伤清单（P0）

### P0-1 急刹一旦触发永远锁死，无法解除

- **证据**：协议文档 [communication_protocol.md](docs/communication_protocol.md) 第 113 行声明 `EBRK` 为 `ON / OFF`（"远程急刹 / 解除急刹"）；但固件 [firmware/arduino/src/main.cpp](firmware/arduino/src/main.cpp) 第 175-183 行的 `EBRK` 分支**只有 ON，没有 OFF 分支**；大脑 [car_brain/brain.py](software/raspberry_pi/car_brain/brain.py) 第 131 行 `remote_ebrake()` 也只发 ON，无解除接口；家长端 UI 无"解除急刹"。
- **影响**：一旦急刹（物理按钮或远程触发），车永久停住，只能断电重启。误触一次即当场瘫痪；对 3 岁孩子场景，家长无法及时恢复车辆。
- **修复建议**：
  1. 固件 `EBRK` 分支增加 `OFF`：`g_ebrk=false; g_brake=false; hal_set_brake_light(0); hal_set_motor(0)`（解除后动力仍先归零，等下次油门才动，防突然窜出）。
  2. 大脑增加 `release_ebrake()`，家长端加"解除急刹"按钮。
  3. 明确**解除的授权**：只有家长端可解除，小车端（孩子）不应能解除。
- **验收标准**：家长端"急刹"→ 车停 → 家长端"解除"→ 车可恢复行驶；固件单元测试覆盖 EBRK ON 与 OFF 两种状态。

### P0-2 控制 API / WebSocket 零鉴权，局域网任意设备可遥控载人车

- **证据**：小车端 8000 / 家长端 8001 绑定 `0.0.0.0`（[digital_twin/backend/twin_server.py](software/raspberry_pi/digital_twin/backend/twin_server.py) 第 552、557 行），README 引导手机用局域网 IP 访问；`/api/control`（第 473-499 行）无任何认证，干杯助手 MCP 工具也全走此无鉴权 API；WebSocket 同无鉴权。
- **影响**：家庭 Wi-Fi 内任意设备可远程急刹 / 改挡 / 鸣笛 / 上下电，涉及人身安全与信息泄露（GPS 轨迹）。
- **修复建议**：
  1. 家长端与管理 API 增加**共享密钥/token**（简单密码即可，真车场景不必过度工程）。
  2. WebSocket 握手校验 token，`/api/control` 校验请求头 token。
  3. 令牌通过环境变量/配置文件注入，不入库、不进前端源码。
- **验收标准**：无 token 访问 8001 页面与 `/api/control` 被拒；带正确 token 正常；伪造 token 失败。

### P0-3 家长端"上下电"在真实模式是崩溃路径

- **证据**：家长端 `seat` 命令 → [twin_server.py](software/raspberry_pi/digital_twin/backend/twin_server.py) 第 202 行调 `self.ceb.set_seat(...)`；仿真模式 `CerebellumSim` 有 `set_seat`，但真实模式 `RealCerebellum`（第 79-100 行）**无此方法**，调用即 `AttributeError`；且固件无 SEAT 命令处理、无座位传感器上报。
- **影响**：真实模式下家长点"下电/上电"→ 后端进程崩溃；"上下电"功能在真车上实际不存在。
- **修复建议**：
  1. 二选一：(a) 实现真实上下电链路（固件加 SEAT 命令 + 座位/继电器），或 (b) 真实模式下将"上下电"按钮置灰并提示"暂不支持"。
  2. 若短期不做真车上下电，至少让 `RealCerebellum` 提供 `set_seat` 空实现 + 明确置灰，**杜绝崩溃**。
- **验收标准**：真实模式下点击"上下电"不崩溃；UI 明确标注能力边界。

## 二、高风险项（P1）

### P1-1 所有"真实模式"代码从未真机联调，且状态值全为模拟

- **证据**：待办记录"拿到树莓派后 ③ `--real-serial` 上板实测"（未做）；固件 [main.cpp](firmware/arduino/src/main.cpp) 第 76-95 行 `estimate_speed` / `adc_to_voltage` / `adc_to_temp` 全为**模拟换算**，注释自标"接入真实传感器后需重新标定"。当前挡位限速、电压电量、温度均为假值。
- **影响**：P0-1、P0-3 之所以漏掉，根因正是从未真机联调；真车一接，所有状态显示错误。
- **修复建议**：上真车前先补两类测试（见 P2-2），再按 [hardware_io_map.md](docs/hardware_io_map.md) 实际接线重新标定 ADC。
- **验收标准**：真机实测油门/电压/温度与真实值误差在可接受范围；`--real-serial` 下跑通完整驾驶流程。

### P1-2 失联（大脑崩溃/断线）无失效安全动作

- **证据**：大脑心跳仅发 `offline` 事件（[brain.py](software/raspberry_pi/car_brain/brain.py) 第 169 行），不触发任何动作；协议文档承诺"失联进入安全模式"，未实现。
- **影响**：树莓派崩溃/断线时，小脑保持最后挡位继续让孩子驾驶，无降速/停车。
- **修复建议**：心跳连续丢失（如 3 次）后，小脑自动降速或停车（fail-safe）。最简实现：小脑侧看门狗——超过 N 秒未收到 PING 即 `hal_set_motor(0)` 并锁 1 挡。
- **验收标准**：人为断开串口/杀进程，N 秒内车停且提示失联。

## 三、工程问题（P2）

### P2-1 文档与实现脱节成体系

- **证据**：`SEAT`（上行/上下电）、`EBRK:OFF`（解除急刹）、EBRK 可靠投递（每 100ms 重发至 ACK 或 2s 超时进安全模式）、失联安全模式——**文档均声明，代码均未实现**。详见 [communication_protocol.md](docs/communication_protocol.md) 第 113、125、182-186 行。
- **影响**：开发按文档联调必然踩坑；文档描述的是一个未做出来的系统。
- **修复建议**：要么实现，要么改文档，二选一，必须与实际代码一致。建议以"代码为准"，在文档对应条目标注"未实现 / 待实现"。
- **验收标准**：协议文档中每条命令在固件 + 大脑两侧都能找到对应实现；反之亦然。

### P2-2 测试只覆盖"文档好路径"，未覆盖"真实坏路径"

- **证据**：现有固件/大脑测试覆盖命令正常处理与仿真链路，但无**真实串口噪声 / 粘包 / 断包 / CRC 失败注入**、无**急刹恢复**、无**失联 fail-safe** 测试。
- **影响**：P0-1、P1-2 未被测试兜住。
- **修复建议**：新增测试组：
  - 串口鲁棒性：注入噪声字节、半个帧、粘连多帧、损坏 CRC，验证不崩溃、能重同步。
  - 急刹：EBRK ON→车停；EBRK OFF→可恢复；物理按钮触发的本地急刹。
  - 失联：断开心跳后小脑降速/停车。
- **验收标准**：以上用例全部通过，并纳入持续集成。

### P2-3 真实模式网页油门/刹车/转向语义割裂

- **证据**：真实模式下网页油门/刹车/转向"仅展示不发命令"（[twin_server.py](software/raspberry_pi/digital_twin/backend/twin_server.py) 第 82-92 行），但 UI 未标注。
- **影响**：家长端可能误以为能远程控车，实际无效，产生误导。
- **修复建议**：真实模式下对无效控件明确标注"真实模式下由物理踏板/方向盘控制，此控件仅显示"。
- **验收标准**：真实模式 UI 有清晰能力边界提示。

### P2-4 后端单文件 + 全局副作用

- **证据**：[twin_server.py](software/raspberry_pi/digital_twin/backend/twin_server.py) 581 行承载 HTTP/WS/语音/GPS/对讲/视频/大脑适配/核心逻辑；第 365 行 `core = TwinCore()` 在 import 即执行，`main()` 又重建。
- **影响**：可维护性差、导入即副作用，测试与复用困难。
- **修复建议**：将 core 初始化收敛进 `main()` 或惰性创建；按职责拆分模块（http / ws / core / media）。
- **验收标准**：import 不触发副作用；模块职责单一。

## 五、建议的落地顺序（给开发）

1. **先修 P0 三项**（急刹解除 / 鉴权 / 上下电崩溃）——这三项决定真车安全性。
2. **补真实串口 + 急刹恢复测试**（P2-2）——在真机联调之前，用测试把"真实坏路径"兜住。
3. **协议文档与代码对齐**（P2-1）——否则联调必踩坑。
4. **再做 `--real-serial` 真机联调**，并完成 ADC 标定（P1-1）。
5. 过程中顺手处理 P1-2（失联 fail-safe）与 P2-3、P2-4。
