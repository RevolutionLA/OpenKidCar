日期：2026-08-07

## 今天的核心思路

今天的开发主线，是一个经典的嵌入式概念：

> **上位机（大脑）与下位机（小脑）的分层架构。**

我用"大脑 / 小脑"来做类比：

- **大脑（上位机）**：树莓派 —— 负责决策、AI 交互、语音识别、高级逻辑。
  它的特点是要算力、要内存，但不需要毫秒级实时响应。
- **小脑（下位机）**：Arduino —— 负责感知与执行。
  它的特点是没有操作系统、时序确定，能在毫秒级响应用户的操作（油门、刹车、灯光）。

这两者通过 **UART 串口 + 自定义协议**通信，形成一条完整的链路：

```
你的操作 → 小脑感知（踏板/按钮） → 协议上报 → 大脑决策 → 协议下发 → 小脑执行 → 状态回传
```

## 今天完成的东西

### 1. 协议（地基中的地基）
- 协议文档升级到 V0.3：CRC8 校验、最大帧长、帧重同步、统一 ACK、安全命令可靠投递
- 两端（Python 大脑 + C++ 小脑）协议实现，CRC 值、帧格式完全一致，测试通过

### 2. 代码骨架（HAL 分层）
- **firmware/arduino**：PlatformIO 工程，`native`（PC 测试）+ `mega2560`（真实固件）双环境
- **lib/protocol**：纯 C++ 协议模块（CRC8 / 帧封装 / 命令常量）
- **src/hal**：硬件抽象层 —— 逻辑层只调 `hal_*` 接口，桌面模拟和真实引脚只是不同实现
- **software/raspberry_pi**：Python 大脑（状态机 / 心跳 / 按钮决策 / 串口通信）
- 验证：Arduino native 协议测试 10/10、Mega 2560 固件编译通过、Python 测试 15 项通过

### 3. 语音控制
- vosk 离线中文识别，唤醒词"干杯出来"
- 可添加/删除指令（指令表化）
- 可换音色（edge-tts 神经语音）

### 4. 数字孪生网页（今天失败的一环）
- 用 Three.js 做了 3D 驾驶舱：3D 车模、HUD、油门/刹车/转向、引擎声、摄像头、对讲
- 前端 ↔ WebSocket ↔ Python 后端（真实 Brain + CerebellumSim）
- **但这一版失败了**：车模方向、灯光位置、转向、布局……反复调试仍不满意

## 作为一个开发小白，我问过的问题（都很有价值）

今天和 AI 的对话中，我作为一个小白开发者问了很多问题。回头看我问的这些问题，其实是每个初学者都会遇到、也都很关键的问题：

1. **大脑/小脑类比科学吗？** —— 答案：科学，这就是上位机/下位机架构，真实汽车也是这么分层的。
2. **代码能直接移植到树莓派/Arduino 吗？** —— 只要分层正确（HAL），逻辑层原样移植，只换硬件层。
3. **桌面模拟器是"一比一"复刻现实吗？** —— 不是，它模拟的是逻辑，不是物理（传感器噪声、电机惯性无法模拟）。
4. **先设计硬件还是先写软件？** —— 先定"接口契约"（引脚、协议），然后两边并行。
5. **协议是什么？为什么要校验？** —— 是两端通信的语言规则；校验防止"传错了还当真"。
6. **要先把所有硬件/功能想全才能定义协议吗？** —— 不需要，定功能清单 + 接口契约即可，器件型号后定。
7. **现有开源车模能用吗？** —— 尝试了多个开源模型，但 AI 生成的模型质量差（碎片化），手动建模的又下载不到。
8. **数字孪生真的是"大脑+小脑"在交互吗？** —— 架构上是的，物理模型真实度要逐步精细化。

这些问题本身，就是这个项目宝贵的知识沉淀。

## 数字孪生失败的教训

今天最后被"数字孪生页面"折磨了很久。反思下来，几个教训值得记录：

1. **看不到渲染结果的盲改是灾难**：我无法直接看到浏览器画面，只能靠代码推理和截图亮度分析。在车模方向、灯光位置这种纯视觉问题上，盲改 + 反复失败是必然的。**教训：视觉类问题，应该优先让用户可调/可验证，而不是猜。**
2. **缓存问题会制造"没变"的假象**：改了很多，用户刷新却"完全没变"，最后发现是浏览器缓存。已通过服务器强制 no-cache 根治。
3. **模型方向要"跟节点走"而不是"猜坐标"**：反复猜车头方向失败后，正确思路是把灯光直接挂到模型的真实车灯节点上。
4. **物理模型要真实**：之前速度是"油门瞬间映射"（刹车不参与），被用户指出后改成积分式物理（加速/减速）。
