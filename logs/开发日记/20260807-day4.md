### 2. 重新设计：一套大脑小脑，两个网页端

关键架构决策 —— **不是两个程序，而是一个核心进程开两个网页**：

```
                一个进程：TwinCore（真实 Brain + CerebellumSim）
                 ├─ http://localhost:8000  → 小车端（仪表盘区 + 控制区）
                 └─ http://localhost:8001  → 家长端（GPS/电量/对讲/视频）
                 └─ /ws 与 /ws_parent 两个 WebSocket，连的是同一辆车
```

- 两端看到**同一辆车的真实状态**（不是各模拟一份）
- 对讲、视频帧通过 WebSocket 在两端互转
- 新模拟数据按真实硬件分层：
  - **GPS** → 大脑层模拟（真实是树莓派读 4G/GPS 模块），随车速移动、带卫星数
  - **电量** → 小脑层模拟（真实是小脑 ADC 上报电池电压），按负载消耗

### 3. 小车端（8000）：仪表盘区 + 控制区
- **仪表盘区**：环形速度表（签名元素）、油门/刹车/电机条、电量/电压/电流/温度、GPS 坐标、6 个灯光状态灯
- **控制区**：档位 1-4、转向手柄、油门/刹车竖向滑杆、大灯/静音/灯带/喇叭开关、急刹大按钮、语音控制、对讲家长
- 深空科技风：深蓝黑底 + 细网格 + 青色发光强调

### 4. 家长端（8001）：手机友好
- **孩子车辆卡**：速度、档位、油门、急刹状态
- **GPS 实时定位**：Canvas 绘制轨迹地图（孩子位置/轨迹/家的坐标），实时经纬度、卫星数、朝向
- **电量卡**：电池百分比大图标、电压/电流/温度
- **视频通话**：一键呼叫孩子 → 双方开摄像头 → 画面互传（真实管线）
- **对讲机**：按住说话 → 孩子那边响起（双向 PTT）
- **远程急刹**：紧急停车按钮

## 踩坑记录（今天修掉的 bug）

1. **aiohttp `add_static("/", dir)` 404**：挂载根路径在 aiohttp 3.14 行为异常。改为显式 `add_get("/")` 返回 index.html + `add_static("/static")` 服务其余资源，干净可靠。
2. **`ws.send_str()` 是异步协程**：在转发对讲/视频时忘记 `await`，导致消息从未真正发出（报 RuntimeWarning）。→ 改成 async 函数 + `await`。
3. **DOM `childNodes[2]` 越界**：家长端在线状态 chip 的 childNodes 只有 2 项，索引 2 是 undefined，导致整个状态渲染中断（GPS 全不显示）。→ 改用独立的 `<span>` + `textContent`，不依赖脆弱的节点索引。
4. **headless Chrome 验证的假象**：`--virtual-time-budget` 会"冻结真实时间"，导致 WebSocket 消息在虚拟时间模式下送不到，页面显示"没渲染"。**这不是 bug，是验证方法的坑**。最终用 Node 原生 WebSocket 以浏览器视角直连，确认数据链路畅通。

## 小白问答沉淀（今天的）

1. **为什么要"一个进程开两个网页"，而不是两个独立程序？** —— 因为两个孩子/家长端要看到**同一辆车**。两个程序各跑一套大脑小脑，状态就分叉了。共享一个核心，才保证"真"。
2. **对讲机"按住说话"是怎么实现的？** —— 按下时用 MediaRecorder 录音，松开时把录音 blob 通过 WebSocket 发给对方，对方用 `<audio>` 播放。是真实的音频管线，不是假象。
3. **视频通话没有 WebRTC 也能做？** —— 可以。用 canvas 每 0.2 秒截一帧摄像头画面（JPEG），通过 WebSocket 发给对方实时显示。局域网下完全够用，还更简单可靠。
4. **GPS 是模拟的吗？** —— 是。真实硬件里 GPS 来自树莓派接的 4G/GPS 模块；现在没有硬件，就在大脑层模拟：车速越快，坐标移动越快，行驶中缓慢转弯形成轨迹。
5. **电量也是模拟的？** —— 是。真实小脑通过 ADC 上报电池电压；现在在小脑模拟层让它按负载（油门）消耗，电压换算成百分比，家长端就能看到"掉电"。

## 速度环"常亮蓝弧" bug（SVG dasharray 原理）

用户框出"速度0时外圈却有一段蓝色弧"，以为是没用的装饰。真相是**速度进度弧的 SVG 写法错了**：

- 错误写法：`stroke-dasharray: 433.5`（dash 段固定占圆周 75%）。闭合圆上 dash 段永远显示，**弧和 offset 无关，永远显示 270°**。
- 正确写法：**JS 动态设置 dasharray** —— `dash = 弧长×速度比例，gap = 周长−dash`，offset 固定 0。速度 0 → dash 0 → 完全隐藏；满速 → dash 433.5 → 270°。
- 验证：像素级确认速度 0 弧 0°、速度 10/15 弧约 180°、速度 0 又归 0°。

**经验**：SVG 环形进度条，`dasharray` 的 dash 段长度必须随进度**动态变化**，不能固定值 + offset 旋转。

## 第二轮体验反馈修复（音效 / 控制区 / 单向视频）

1. **音效无声**：Web Audio 引擎轰鸣 + 喇叭在点击时无声。根因：浏览器自动播放策略把 `AudioContext` 挂起（suspended），需在用户手势后 `resume()`。修复后：`initAudio()` 检测到 suspended 就 resume；并把引擎声音量曲线改为"油门 0 几乎无声、油门越大越响"。
2. **控制区重布局**：油门/刹车 → 竖向瘦长滑块（`writing-mode: vertical-lr`）；转向手柄 → 横向瘦长；8 个功能按钮（大灯/静音/灯带/喇叭/急刹/语音/视频/对讲）统一为 2×4 等大小方块（含按住对讲）。
3. **视频改为单向视频、双向语音**：小车端只推自己的摄像头画面给家长，不再接收/显示家长视频流；家长端只显示孩子画面、不推自己的视频；对讲（PTT）仍双向。
4. **电池消耗速率调低**：原来约 42 分钟耗尽太夸张，调整为约 5.5 小时，演示更真实。
5. **链路测试增强**：`test_ws_link.py` 的急刹项改为等待状态同步（修掉时序竞争，6/6 稳定通过）。

**经验**：浏览器无声类问题，90% 是 `AudioContext` 没 `resume()`（autoplay 策略），不是引擎代码错。

### 控制区再调整（第三轮）：操控杆加长 + 按钮排两侧

用户反馈控制区有空白、杆太短。改为"驾驶舱"三分布局：

- **中间**：油门、刹车两个竖向长杆（426px，约占控制区 2/3），随高度 flex 拉伸
- **左右两侧**：各 4 个统一大小按钮竖排（左：大灯/静音/灯带/喇叭；右：急刹/语音/视频/对讲）
- grid 三列 `1fr auto 1fr`，DOM 精确验证：左右对称、杆长、无空白无重叠

**经验**：验证布局要设置与用户一致的视口（Emulation.setDeviceMetricsOverride），否则默认小视口触发响应式布局，坐标全错。

### 控制区再调整（第四轮）：杆与按钮等高 + 整体居中

用户反馈竖杆 426px 太长（比按钮长一倍）、周围大量空白。用 DOM 精确测量发现：主区 flex:1 撑满 447px，杆撑满导致超长，按钮只有 200px 悬在中间。

修复：杆固定 240px 与按钮列完全等高（4 按钮 padding 15px），主区 `align-items: center` 让杆+按钮整体垂直居中，上下留白对称（105/127→93/93）。视觉确认"布局协调"。

**经验**：控件高度不匹配是"大量空白"的根源 —— 元素等高 + 整体居中，留白自然对称。
